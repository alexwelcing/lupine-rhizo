# Lean Spec

`lean-spec/` holds Lean 4 statements over recorded values and idealized models.
Lean 4 checks the arithmetic and stated inequalities behind published numbers; it
does not check the physics, the reference data or the pipeline. A green build means
the recorded numbers satisfy the stated inequalities and the stated lemmas follow
from their hypotheses. It does not show that a material behaves as a model assumes,
so a Lean statement never supports an empirical claim on its own (badge: "Lean-checked
arithmetic"; see the [formal proof ledger](../docs/formal-proof-ledger.md)).

Many declarations are single-tactic checks of recorded numbers (`decide`,
`native_decide`, `norm_num`); `native_decide` additionally trusts Lean's compiled
evaluator. The generated count in [`theorem-count.json`](theorem-count.json) measures
how many statements are checked, not how much physics is validated.

## Current state

- The current theorem inventory is generated from the Lean source into [`theorem-count.json`](theorem-count.json); never transcribe its count into this README. The build is locked by `#guard` contracts in `Materials/Vision.lean`, and the generated inventory must report zero `sorry` proofs.
- Epistemic gaps are documented as structures/comments, not as axioms.
- The climate-series modules (`Theory/BarrierArrhenius`,
  `Theory/RankingIntegrity`, `Theory/ScalingVolcano`,
  `Theory/DefectStability`, `Theory/SorptionStability`,
  `Validation/ClimateSeries`, `Validation/ClimatePortfolio`) are definitions
  and consistency checks for idealized models (Arrhenius barriers, competitive
  Langmuir sorption, scaling relations, defect stability) and integer checks of
  arithmetic quoted in earlier articles (including the abatement ranges those
  articles quoted, which are not Lupine outcomes). **These modules
  bind no measured data for the five material classes they name** (cobalt-free
  LMR cathodes, halide solid electrolytes, MOF DAC sorbents, electrochemical
  ammonia catalysts, lead-free perovskites); `ClimatePortfolio` records the
  rocksalt/halide layout as data-pending. They describe where the work is aimed,
  not results.
- The measured-fields rung (`Theory/AnchoredField`,
  `Data/EnvFieldInstances`, generated by
  `python/scripts/bind_env_field_instances.py`) binds the Y-matrix corpus
  into per-cell field instances at two tiers: every (model, material) cell
  yields a `MeasuredField` (closure/transfer/ranking laws; fcc anchors
  γ₁₀₀→c=8, γ₁₁₁→c=9, E_vac→c=11 pinned at c=12, bcc anchors γ₁₀₀→c=4,
  γ₁₁₀→c=6, E_vac→c=7 pinned at c=8, diamond anchor E_vac→c=3 pinned at
  c=4), and the monotone-softening cells additionally yield an `ErrorField`
  (directional barrier laws) — 68 measured fields (36 fcc + 28 bcc +
  4 diamond), 19 anchored instances, 49 kernel-checked tier-2 refusals; the
  rocksalt cells measure no anchor observables and are documented as
  unbound. The promotion gate mirrors these certificates in
  `python/lupine_distill/odf/field_certificates.py`, the local flywheel
  (`tools/mlip_local_promotion.py`) attaches them to every promotion packet
  and its Phoenix telemetry spans, and the run-time certificate gate
  (`lupine_distill_runtime.policy_engine.CertificateGate`) excludes
  tier-2-refused cells from correction inside the distill policy engine.
- The anchor-identification rung (`Theory/AnchorBracket`,
  `Validation/AnchorBracketCertificates`) proves what a cell's
  measured anchors determine about the error field *under the module's
  softening-field model*: a
  softening field through the anchors exists iff they pass the decidable
  admissibility test (so, within that model, every corpus refusal rules out
  *all* interpolation schemes, not just the step field); on in-range
  configurations the entire remaining ambiguity is one scalar — the field
  value at the single unanchored coordination (fcc c = 10, bcc c = 5,
  none for diamond) — pinned inside the neighboring anchor gap; corrected
  energies therefore carry two-sided error bars, valid under that model, with exact
  per-atom widths (chgnet/Ni 537×10⁻⁴ eV, chgnet/Fe 256×10⁻⁴ eV,
  mace-mp-medium/Ni 81×10⁻⁴ eV; diamond cells are exact), corrected
  rankings are checked against every consistent field by a two-point
  envelope test (with an interval-separation margin rule), corrected
  Arrhenius rates carry multiplicative caps under the model, and below the
  anchored range (or at the measured tier) non-identifiability is proven,
  justifying refusal. The runtime mirror
  (`field_certificates.py`) carries the identification payload
  (gap coordination, bracket width, identification refs) on every anchor
  certificate and exposes the separation rule as
  `check_bracket_separation`.

The current dependency stack is Lean 4.35.0, Mathlib `56a005855ea17e0b0958f73ec801ae140b0a1679`,
and the upstream `atlas` package at `a60759060b5616df0d5775b42da4d337719feb32`.

## Install

Install the Lean toolchain via [elan](https://github.com/leanprover/elan), then
hydrate the Mathlib cache. Full setup is in [`docs/ONBOARDING.md`](../docs/ONBOARDING.md).

## Build

```bash
# Run from INSIDE lean-spec/ so elan selects the pinned v4.35.0 toolchain.
cd lean-spec
lake exe cache get
lake build
```

A green build is the gate. A broken build or any new `sorry` proof is a
regression.

## Check

```bash
# Re-run the full proof build
cd lean-spec
lake build

# Regenerate the authoritative theorem inventory
node scripts/generate-lean-count.mjs
```

## Windows notes

- Always run `lake` from inside `lean-spec/`; running from the repo root selects
  the global toolchain and silently refuses the ATLAS-Lean cache.
- Do **not** import whole ATLAS-Lean subjects (e.g. a complete `MathlibExt` subject). Import
  only proved `MathlibExt`, `CSLibExt`, or `PhyslibExt` leaf modules when needed;
  never import `WantedExt` or build the upstream package's default targets.
